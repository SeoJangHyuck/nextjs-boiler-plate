# Claude Code 가이드라인

## 언어

사용자와 소통할 때는 항상 **한국어**로 응답합니다.

## 프로젝트 참조

작업을 시작하기 전에 다음 문서를 검토하세요:

- `README.md` - 프로젝트 개요, 기술 스택, 구조, 스크립트

## 코드 작성 전 확인사항

1. 작업에 적용되는 규칙 파일을 확인하세요:
   - `.claude/rules/nextjs.md` - Next.js 컴포넌트, 라우팅, 레이아웃
   - `.claude/rules/typescript.md` - 타입 정의, 네이밍, 패턴
   - `.claude/rules/scss.md` - 스타일링, 변수, 믹스인
   - `.claude/rules/tailwind.md` - Tailwind CSS v4, 유틸리티 클래스, 테마
   - `.claude/rules/git.md` - 커밋, 브랜치, 풀 리퀘스트
   - `.claude/rules/zustand.md` - 클라이언트 상태 관리, 스토어, 슬라이스
   - `.claude/rules/zod.md` - 스키마 검증, 폼 통합
   - `.claude/rules/tanstack-query.md` - 서버 상태, 데이터 페칭, 캐싱
   - `.claude/rules/next-intl.md` - 다국어 지원, 번역

2. 코드를 작성하거나 수정하기 전에 관련 규칙을 검토하세요.

3. 규칙을 엄격히 준수하세요. 의문이 있으면 사용자에게 문의하세요.

## 프로젝트 컨텍스트

- **프레임워크**: Next.js 16+ (App Router, Turbopack)
- **언어**: TypeScript 5+ (strict mode)
- **스타일링**: Tailwind CSS 4 + SCSS
- **패키지 매니저**: pnpm
- **다국어**: next-intl (ko, en)
- **인증**: next-auth (OIDC 연동 예정)
- **상태 관리**: Zustand (클라이언트), TanStack Query (서버)

## Superpowers 통합

superpowers 스킬(brainstorming, writing-plans, executing-plans) 사용 시:

1. **설계 문서**: `docs/plans/YYYY-MM-DD-<topic>-design.md`에 저장
2. **프로젝트 규칙 준수**: 코드 생성 시 `.claude/rules/*` 컨벤션 적용
3. **커밋 메시지**: `.claude/rules/git.md` 컨벤션 준수
4. **코드 스타일**: `.claude/rules/typescript.md`와 `.claude/rules/nextjs.md` 준수

### 계획 문서 형식

모든 계획 문서에는 다음이 포함되어야 합니다:

- 목표 (1문장)
- 아키텍처 (2-3문장)
- 프로젝트와의 기술 스택 정합성
- 정확한 파일 경로가 포함된 단계별 작업

## Superpowers 워크플로우 순서

superpowers 명령어 사용 시 반드시 다음 순서를 따르세요:

```
┌─────────────────────────────────────────────────────────────────┐
│  Step 1: /superpowers:brainstorm                                │
│          → 요구사항 탐색, 설계 옵션 논의                        │
│          → 산출물: 명확한 요구사항                              │
├─────────────────────────────────────────────────────────────────┤
│  Step 2: /superpowers:writing-plans                             │
│          → 구현 계획 작성                                       │
│          → 산출물: docs/plans/YYYY-MM-DD-<topic>-design.md      │
├─────────────────────────────────────────────────────────────────┤
│  Step 3: /superpowers:executing-plans                           │
│          → 계획을 작업별로 실행                                 │
│          → 산출물: 구현된 코드                                  │
└─────────────────────────────────────────────────────────────────┘
```

### 규칙

1. **순차적 실행**: 순서대로 진행 (1 → 2 → 3)
2. **산출물 존재 시 건너뛰기**: 이전 단계의 산출물이 있으면 다음 단계로 진행 가능
3. **실행 전 확인**: 진행하기 전에 항상 필요한 산출물이 있는지 확인

### 건너뛰기 조건

| 명령어            | 필요한 산출물            | 건너뛸 수 있는 경우                  |
| ----------------- | ------------------------ | ------------------------------------ |
| `writing-plans`   | brainstorming 산출물     | 이전 대화에서 요구사항이 정리된 경우 |
| `executing-plans` | `docs/plans/*-design.md` | 설계 문서가 이미 존재하는 경우       |

```
✅ OK: 요구사항이 있으면 brainstorming 건너뛰기
User: "/superpowers:writing-plans"
Claude: *컨텍스트에서 요구사항이 명확한지 확인*
        → 있으면: 계획 작성 진행
        → 없으면: "먼저 brainstorming을 통해 요구사항을 정리해주세요."

✅ OK: 계획이 있으면 실행으로 건너뛰기
User: "/superpowers:executing-plans"
Claude: *docs/plans/*-design.md 확인*
        → 있으면: "기존 설계 문서를 기반으로 실행합니다."
        → 없으면: "먼저 writing-plans로 설계 문서를 작성해주세요."
```

## 작업 완료 플로우

**중요**: 작업 완료 후 자동으로 커밋하지 마세요. 반드시 사용자 검토를 요청하고 명시적 승인을 받은 후에만 커밋하세요.

### 워크플로우

```
┌─────────────────────────────────────────────────────────────────┐
│  Step 1: 작업 완료                                               │
│          → 코드 작성/수정 완료                                   │
├─────────────────────────────────────────────────────────────────┤
│  Step 2: 변경사항 요약                                           │
│          → 무엇을 변경했는지 사용자에게 설명                     │
│          → 변경된 파일 목록 제시                                 │
├─────────────────────────────────────────────────────────────────┤
│  Step 3: 사용자 검토 요청                                        │
│          → 변경사항을 검토해달라고 요청                          │
│          → 사용자가 코드를 확인할 시간 제공                      │
├─────────────────────────────────────────────────────────────────┤
│  Step 4: 커밋 승인 요청                                          │
│          → 커밋을 진행할지 질문                                  │
│          → 사용자가 명시적으로 승인한 경우에만 커밋              │
│          → `.claude/rules/git.md` 컨벤션 준수                    │
└─────────────────────────────────────────────────────────────────┘
```

### 규칙

1. **자동 커밋 금지**: 작업 완료 후 절대 자동으로 커밋하지 않음
2. **검토 우선**: 커밋 전 반드시 사용자 검토 요청
3. **명시적 승인**: 사용자가 명시적으로 승인한 경우에만 커밋
4. **Git 규칙 준수**: 커밋 시 `.claude/rules/git.md` 컨벤션 적용

### 예시 상호작용

```
✅ 올바른 플로우:
Claude: 작업이 완료되었습니다.

        **변경사항:**
        - `src/components/Button.tsx` - 버튼 컴포넌트 추가
        - `src/styles/button.scss` - 버튼 스타일 추가

        변경사항을 검토해주세요.
        검토 완료 후 커밋을 진행할까요?

User: 네, 커밋해주세요.

Claude: `.claude/rules/git.md` 규칙에 따라 커밋을 진행합니다.
        *커밋 진행*

❌ 잘못된 플로우:
Claude: 작업이 완료되었습니다. 커밋합니다.
        *묻지 않고 자동으로 커밋*
```

### 사용자가 커밋을 요청한 경우

사용자가 직접 커밋을 요청한 경우에도:

1. 변경사항 요약 제시
2. `.claude/rules/git.md`를 따르는 커밋 메시지 제안
3. 최종 확인 후 커밋 진행
